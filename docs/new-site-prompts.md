# 新站点汉化提示词

用途：让 AI 代理（Codex 等）用浏览器控制扫描一个网站的每个页面、每个弹窗、每个状态，翻译界面文字，产出符合 [RULES.md](../RULES.md) 固定模式的 Tampermonkey 简体中文汉化脚本。示例站点是 OpenRouter。
换站点：改【总则】顶部的变量，并把各阶段里的 `openrouter` 换成新站点的英文名。

## 先看这三点

1. **"不漏任何细节"一次扫描做不到。** 弹窗、tooltip、Toast、空状态、错误提示关闭后 DOM 里都没有；有些状态要付费或真实数据才出现。可靠做法是闭环：采集 → 翻译 → 装上脚本重放每个页面状态 → 自动扫描残留英文 → 补词典 → 重复到残留为 0。核心是阶段 4。仍覆盖不到的（Stripe 等跨域 iframe、canvas 里的字、服务器返回的英文报错、没触发过的状态）必须列进"无法覆盖清单"，不能说成已覆盖。
2. **不能一个超长提示词一口气发。** Codex 会丢上下文、偷懒。所以拆成阶段，每阶段产出落成文件，下阶段读文件，不靠对话记忆。
3. **"所有内容"要划界：只翻译界面文案，不翻译第三方/用户数据。** OpenRouter 的模型名、模型和供应商描述、日志里的提示词正文都是动态英文数据，静态词典翻不完也不该翻。想翻这类内容只能接在线翻译 API，有隐私和费用问题，不在本方案内。总则里的 `THIRD_PARTY_CONTENT` 默认是"不翻译"。

另：只是自己读得懂的话，Chrome 自带整页翻译零成本。做油猴脚本值得的前提是要长期用、术语要统一、不想每次手点翻译。

## 使用步骤

1. 新开一个 AI 会话，工作目录选**仓库之外的空目录**。采集阶段的文件含有真实页面内容，不能放进仓库。
2. 在 Codex 控制的浏览器里**你自己登录**（含二步验证），不要把密码给 Codex。
3. 粘贴【总则】，改好顶部变量。
4. 依次粘贴阶段 1 → 4。每阶段 Codex 给出"阶段完成报告"后再发下一段。阶段 1 结束有检查点：你确认页面范围，回复"确认范围"。
5. 最终拿 `*.user.js` 装进 Tampermonkey。站点改版后用【维护段】补漏。

## 【总则】（第一条消息，先发这个）

```
# 角色与目标
你是前端本地化工程师。目标：为网站 {SITE_NAME} 制作一个 Tampermonkey 简体中文汉化脚本，覆盖 {SCOPE} 内每一个页面、每一处可见文字，包括：按钮点开后的弹窗/抽屉、下拉菜单、标签页、折叠区、tooltip、空状态、加载态、错误提示、表单校验提示、Toast、确认对话框。

# 变量（我已填写，按此执行）
- SITE_NAME: OpenRouter
- START_URL: https://openrouter.ai/
- SCOPE: 登录后的账户/Dashboard 区域的全部页面（具体有哪些，以你在站点上实际发现为准）。文档站不在范围内。
- THIRD_PARTY_CONTENT: 不翻译。包括模型名称、模型/供应商描述、用户输入的内容、提示词与日志正文、代码、API 密钥、URL、数字、金额、模型 slug。
- OUTPUT_DIR: 当前工作目录

# 硬性规则（优先级最高，任何阶段都适用）
## 安全
1. 只读探索。可以点击打开弹窗、菜单、标签页、展开项。遇到会产生真实后果的最终确认（删除密钥/账号、购买积分、提交付款、撤销授权、发送邀请、保存会改变账户设置的表单），一律不要确认：读完文字后点取消或关闭。
2. 不要为了看界面而创建、修改、删除任何资源（密钥、预设、工作区、成员等）。需要这样才能看到的界面，记入"未覆盖清单"并告诉我，由我决定。
3. 登录由我手动完成。不要索要、输入、记录任何密码、验证码、Cookie、token。
4. API 密钥、邮箱、账号 ID、订单号、余额等个人数据，不得写入任何输出文件（词典、报告、文件名）。截图只存本地，且不得包含密钥全文。遇到这类动态值，用正则或占位处理。
## 方法
5. 不凭记忆或猜测。每一条待翻译的英文，必须来自你在页面上实际看到的文本，并记录来源页面和状态。
6. 做不到、没验证的，如实标注"未验证/未覆盖"，不得写成已完成。
7. 每个阶段开始前，先读取上一阶段在 OUTPUT_DIR 里的产出文件，不要依赖对话记忆。

# 产出文件（均放在 OUTPUT_DIR）
- 01-sitemap.md：站点地图与状态清单
- 02-strings/<页面slug>.json：每页每状态采集到的文本
- 02-summary.md：采集汇总与遗漏风险
- glossary.md：术语表
- openrouter-zh-cn.user.js：最终脚本（单文件）
- 03-residual.json：残留英文扫描结果
- coverage-report.md：覆盖报告

# 每阶段结束时
输出"阶段完成报告"：做了什么、产出了哪些文件、未完成/未验证项、需要我做什么。然后停下，等我指令。不要自动进入下一阶段。

现在不要开始工作，回复"总则已收到"，并复述你理解的 SCOPE 和 THIRD_PARTY_CONTENT。
```

## 【阶段 1：勘察与站点地图】

```
开始阶段 1：勘察。本阶段只看、不采集全文、不写脚本。

1. 打开 START_URL，确认我已登录（能看到账户区域）。未登录就停下来，让我登录。
2. 枚举所有页面入口：侧边栏、顶部导航、用户头像菜单、页脚、设置页内部标签、页面内链接、面包屑。逐个访问。动态路径用 :id 表示。同类详情页只取 1–2 个代表。
3. 对每个页面，列出"状态清单"，逐项判断是否存在：
   - 标签页、筛选/排序下拉、分页
   - 表格行的 ⋯ 菜单、行内操作
   - 按钮触发的弹窗/抽屉/确认框（只打开，不确认）
   - 折叠面板、开关切换后的文案变化
   - tooltip/hover 提示、图表悬停提示
   - 空状态、加载中、错误状态
   - 表单校验提示（仅限留空等被前端拦截、不会写入数据的触发方式）
   - Toast/通知
   - 窄屏（手机宽度）下才出现的菜单或布局
4. 标出脚本翻译不到的东西：跨域 iframe（如支付 Stripe）、canvas 绘制的文字、图片里的文字、需要真实付费或真实数据才出现的状态。
5. 技术侦察，写清结论：
   - 是否 React/Next 等 SPA；页面跳转是否不刷新（决定脚本要不要监听路由变化）
   - 是否用了 Shadow DOM
   - `<html lang>` 是什么；站点自己有没有语言切换/中文版（有的话先告诉我）
   - 图表文字是 SVG 还是 canvas
6. 输出 01-sitemap.md，表格列：页面名 | URL 模式 | 状态清单 | 前置条件（需要有哪些数据才显示）| 脚本无法覆盖的部分 | 需要我协助的事。

检查点：写完后把站点地图的摘要发给我，停下，等我回复"确认范围"再进入阶段 2。
```

## 【阶段 2：文本采集（逐页、逐状态）】

```
开始阶段 2：文本采集。先读 01-sitemap.md。

1. 先写一个可复用的页内提取脚本（在页面里运行），一次采集以下内容：
   - 所有可见文本节点；排除 script/style/noscript/code/pre/textarea/input 的 value/contenteditable
   - 属性文字：placeholder、title、aria-label、alt、aria-description、按钮型 input 的 value、<option> 文本，以及这个站点实际用到的其他自定义文字属性（先观察再决定）
   - document.title
   对每条记录：原文、规范化后的原文（trim + 合并连续空白）、类型（text 或 attr:名称）、所在元素的标签和选择器线索、是否碎片化（所在句子被拆在多个文本节点里，例如 `You have <b>3</b> keys`）、是否含动态值（数字、金额、日期、用户数据）。
2. 对 01-sitemap.md 里每个页面的每个状态，按「触发状态 → 等渲染稳定 → 运行提取 → 去重合并」执行，保存为 02-strings/<页面slug>.json。
   - 弹窗、下拉、tooltip、抽屉关闭后 DOM 里通常没有，必须每个单独触发、单独采集。
   - 长页面滚到底；展开所有折叠区；表格切换分页。
   - Toast 等瞬时提示：先在页面挂 MutationObserver，再触发动作，捕获出现过的文本。
3. 动态文本做成模板：同一句话里的变化部分用 {n}、{amount}、{date} 占位，并记录至少 2 个你见过的真实实例作为证据（例如 "3 days ago" / "12 days ago"）。个人数据只记模板，不记真实值。
4. 碎片化句子：记录它的 DOM 结构（每个文本节点各是什么），阶段 3 单独处理。
5. 每个页面采集完做自检：对比页面截图与已采集文本，找出屏幕上看得见、但没采到的英文（常见遗漏：hover 内容、懒加载内容、折叠区、滚动区域内部）。有遗漏就补采。
6. 输出 02-summary.md：每页每状态的条数、碎片化条数、仍可能遗漏的风险点。

完成后给出阶段完成报告，停下。
```

## 【阶段 3：翻译与脚本制作】

```
开始阶段 3：翻译与制作脚本。先读 02-strings/ 全部文件和 02-summary.md。

## 一、术语表（先做）
先写 glossary.md：把高频、多义、专业的词统一译法并说明理由（例如 Credits、API Key、Activity、Provider、Token、Prompt、Rate limit、Workspace、Preset 等，以实际出现的为准）。
- 不翻译：品牌/产品名（OpenRouter、Stripe、GitHub、Google 等）、API/SDK/JSON/HTTP/URL/ID 等缩写、代码、模型名、快捷键字符、货币符号。
- 译法面向开发者/技术用户，风格与主流产品的中文控制台一致，简洁，不用翻译腔。
- 同一英文在不同语境意思不同（例如 Reset、Limit、Key、Credit 名词/动词），要按页面区分，并在词典里支持"按路径覆盖"。
- 按钮、标签、表头保持简短，避免中文撑破布局。句末标点用中文标点。变量部分原样保留。

## 二、脚本技术要求（单文件 openrouter-zh-cn.user.js）
1. 头部、开头注释、代码结构，一律按开源仓库 RULES.md 第 3 节的固定模式，字段和顺序如下（站点名、域名按实际改）：
   ```
   // ==UserScript==
   // @name         OpenRouter 简体中文
   // @namespace    https://github.com/asiananlee/zh-cn-userscripts
   // @version      0.1.0
   // @description  OpenRouter 控制台的简体中文界面；保留用户内容、代码和凭据。
   // @author       asiananlee
   // @license      MIT
   // @homepageURL  https://github.com/asiananlee/zh-cn-userscripts
   // @supportURL   https://github.com/asiananlee/zh-cn-userscripts/issues
   // @match        https://openrouter.ai/*
   // @run-at       document-start
   // @grant        none
   // ==/UserScript==
   ```
   不要写 `@updateURL` 和 `@downloadURL`，发布时由我补。`@run-at` 如果不用 document-start，在注释里写明理由。
   头部后紧跟一段注释，必须包含：`最后核对：YYYY-MM-DD`、覆盖范围、已知未覆盖、不翻译的内容、调试开关的键名与开关方法。注释里不写生成过程、工作目录、内部文件名。
   代码从上到下依次为：COMMON_EXACT 与 COMMON_RULES（公共词典）→ SCOPES（页面分区，每个分区有 id、slug、path、exact、rules、overrides、fragments，前一行注释写 id、slug 和路径）→ ATTRS 与 BLOCK（属性白名单、跳过区域）→ 引擎。
2. 匹配机制（按此顺序）：
   a. 精确匹配：对文本节点取"规范化后的完整文本"查词典（Map）；命中后保留原节点首尾空白。
   b. 正则/模板规则：处理含动态值的句子，必须用 ^ $ 锚定，防止误伤。
   c. 碎片化句子：逐个文本节点分别翻译，保证拼起来语序正确；做不到的，用"父元素整体文本匹配成功后，再分别改写各文本节点"的规则。
   d. 属性文字：同样查词典。
   e. 严禁对文本做子串全局替换（会把 Keyboard 里的 Key 换掉），严禁用 innerHTML 或整段 textContent 覆盖含子元素的节点。
3. SPA/React 兼容：
   - 只改文本节点的 nodeValue 和白名单属性，不改元素结构。
   - React 重渲染把英文写回来时，必须能再次翻译（不能因为"已翻译过"标记而跳过新写回的英文）。
   - 用 MutationObserver（childList、subtree、characterData，属性只监听白名单）+ 批处理节流；避免"自己的修改触发自己"的死循环。
   - 监听 pushState/replaceState/popstate，让"按路径覆盖"的规则在不刷新的页面跳转后生效。
4. 跳过区域：script/style/code/pre/textarea/input 的 value/contenteditable，以及阶段 2 记录的"第三方/用户内容"选择器。
5. 调试开关：默认关闭。通过 localStorage 的 `站点名.zhCN.debug` 键（例如 `openrouter.zhCN.debug`，值为 '1'，刷新后生效，键名写进文件开头注释）打开后，在控制台汇总打印"未命中词典的英文文本"。这是日后站点更新时补漏用的。打印前必须脱敏：网址、邮箱、长串、数字、金额、日期换成占位符，资源名、人名、域名等页面上的自由文本凡能识别的位置都要换掉；最多 100 条；不打印用户输入、正文和密钥；不写入任何存储。
6. 性能：大页面不出现可感知的卡顿。
7. 开源仓库的自动检查会拒收下列写法，脚本里一律不要出现：fetch()、XMLHttpRequest、WebSocket、EventSource、sendBeacon、importScripts、eval、new Function、字符串形式的 setTimeout/setInterval、document.write、insertAdjacentHTML、写入 innerHTML/outerHTML、document.cookie、indexedDB、sessionStorage、navigator.clipboard、navigator.credentials、localStorage.setItem（只允许读调试键）、动态创建 script 元素、GM_* 和 GM.*、unsafeWindow、@require、@resource、@connect、@include。词典里的英文原文如果恰好含这些词，只要不是函数调用的写法就没问题，例如 "Failed to fetch"。

## 三、产出
- 词典与规则按页面分区写在脚本里，注释写清每个分区对应哪个页面。
- 用 `node --check` 做语法检查，通过后才算完成。
- 脚本和词典里不得出现任何密钥或个人数据。

完成后给出阶段完成报告（词条数、正则规则数、按路径覆盖的条目数、术语表里的待我拍板项），停下。
```

## 【阶段 4：闭环验证（"不漏"靠这一步）】

```
开始阶段 4：验证并补漏。先读 01-sitemap.md、02-strings/、glossary.md 和 openrouter-zh-cn.user.js。

1. 让脚本在浏览器里生效：优先装进 Tampermonkey；装不了就用自动化工具在每个页面加载前注入同一份脚本文件（addInitScript 之类）。说明你用的是哪种，并确认注入的就是 OUTPUT_DIR 里这个文件。
2. 对 01-sitemap.md 里每个页面 × 每个状态重放一遍（弹窗、下拉、tooltip、Toast 都要重新触发），执行"残留英文扫描"：遍历可见文本节点和白名单属性，找出仍含拉丁字母、且不属于豁免项（品牌名、缩写、代码、模型名、用户数据、纯数字与金额）的文本。结果写入 03-residual.json，字段：页面、状态、原文、类型、选择器线索。
3. 把残留项补进词典或规则，重新装载，重新重放。循环，直到所有已访问的页面状态残留为 0，或剩余项都被明确归入"豁免"或"无法覆盖"。最多迭代 5 轮，仍未清零就如实报告。
4. 额外检查，逐项给出结果：
   - 不刷新、只靠站内跳转切换页面后，翻译是否仍生效
   - 弹窗、下拉、tooltip、Toast 是否已翻译
   - 把窗口缩到手机宽度，是否有中文导致的溢出、换行错乱、按钮被截断；截图对比，有问题就改译文
   - 浏览器控制台无报错；没有 MutationObserver 死循环（观察 CPU 和长任务）
   - 只读操作抽样（点击、下拉选择、复制按钮、输入框输入）功能仍正常
   - 误翻译检查：模型名、API 密钥、代码块、用户输入、URL 保持原样
   - 刷新后是否有明显的英文闪烁（记录即可，不必修）
5. 输出 coverage-report.md（发布时由我整理成仓库里的 docs/站点英文名-coverage.md，结构参照仓库里的 docs/postmark-coverage.md；报告里不要写本机路径、工作目录名、内部脚本名），包含：
   - 页面 × 状态覆盖矩阵（✅ 已验证 / ⚠️ 部分 / ❌ 未覆盖 + 原因）
   - 词条总数、规则数、豁免规则清单
   - 无法覆盖清单：跨域 iframe、canvas、图片文字、需要付费或真实数据才出现的状态、服务器返回的英文报错、你没能触发的状态
   - 已知风险
   - 日后维护方法
6. 最终自检清单（逐条回答是/否）：语法检查通过；@match 正确且不过宽；脚本与报告里无密钥和个人数据；词典无重复键冲突；报告里没有把未验证的内容写成已覆盖。

完成后给出阶段完成报告，停下。
```
